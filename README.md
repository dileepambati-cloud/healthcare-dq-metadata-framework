# Healthcare Data Quality & Metadata Framework

[![CI](https://github.com/dileepambati-cloud/healthcare-dq-metadata-framework/actions/workflows/ci.yml/badge.svg)](https://github.com/dileepambati-cloud/healthcare-dq-metadata-framework/actions/workflows/ci.yml)
![Python](https://img.shields.io/badge/python-3.10%20|%203.11%20|%203.12-blue)
![License](https://img.shields.io/badge/license-MIT-green)

A rule-driven data quality (DQ) engine for healthcare-style datasets (members, claims).
Checks are **not hard-coded** - they live in metadata/config tables, and the engine
reads them at runtime, runs each check, and logs every result. Adding a new check to a
feed means inserting one row into `dq_rule_config`, not writing new code.

> All data in this repo is synthetic and generated by `data/generate_sample_data.py`.

## Why

In most pipelines, validation logic ends up copy-pasted across jobs. When a new feed comes
in, someone writes the same null/duplicate/range checks again. This project pulls that
logic into one place:

- **Config tables** define *which* datasets are checked and *what* rules apply
- **A rule library** holds one small, tested function per rule type
- **The engine** joins the two together and writes results to a log table that
  dashboards and alerts can read

## Architecture

```
 dq_dataset_config ─┐
                    ├──> engine.py ──> rules.py (not_null, unique, range, regex, ...)
 dq_rule_config ────┘        │
                             ├──> dq_result_log   (one row per rule per run)
                             └──> dq_run_log      (one row per run, SUCCESS/WARN/FAILED)
```

| Table | Purpose |
|---|---|
| `dq_dataset_config` | Datasets under monitoring - source type, location, load type, owner |
| `dq_rule_config` | One row per check - rule type, column, JSON params, severity, pass threshold |
| `dq_run_log` | Run-level summary |
| `dq_result_log` | Rule-level results: total, failed, pass %, PASS/FAIL, message |
| `dq_volume_history` | Row count per dataset per run (for volume checks) |
| `dq_schema_baseline` | Expected columns and types per dataset (for drift checks) |

## Supported rule types

| rule_type | What it checks | Example params |
|---|---|---|
| `not_null` | No blank/null values | `{}` |
| `unique` | No duplicate keys | `{}` |
| `allowed_values` | Value is in a list | `{"values": ["PAID","DENIED"]}` |
| `regex` | Value matches a pattern | `{"pattern": "^[0-9]{5}$"}` |
| `range` | Numeric value within bounds | `{"min": 0, "max": 100000}` |
| `date_not_future` | Date is valid and not in the future | `{}` |
| `referential` | Value exists in another dataset (FK check) | `{"ref_dataset": "members", "ref_column": "member_id"}` |
| `row_count` | Dataset has a minimum number of rows | `{"min_rows": 10}` |

### Dataset-level monitors

These look at the whole dataset and keep history between runs.

| rule_type | What it checks | Example params |
|---|---|---|
| `freshness` | Newest timestamp in a column is not older than the limit | `{"max_age_hours": 24}` |
| `volume_anomaly` | Row count is within X% of the average of the last N runs | `{"lookback_runs": 7, "tolerance_pct": 30}` |
| `schema_drift` | No columns added, removed or changed type vs. the stored baseline | `{}` |

The first run captures the baseline schema and the first volume point, so drift and
volume alerts start from the second run. History lives in `dq_volume_history` and
`dq_schema_baseline` (see `sql/ddl/03_monitoring_tables.sql`).

Each rule has a `threshold_pct` - e.g. a zip-code format rule can pass at 95% while a
primary key rule must be 100%. A failed `HIGH` severity rule marks the whole run as `FAILED`.

## Quick start

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python data/generate_sample_data.py   # creates data/sample/*.csv
python run_dq.py                      # runs all active rules
python run_dq.py --db dq.db           # keep history in a file so volume/drift checks have a baseline
python -m pytest -q                   # unit + engine tests
```

### Sources

| source_type | source_location | Driver |
|---|---|---|
| `csv` | path to file | built in |
| `snowflake` (or `table`) | `DB.SCHEMA.TABLE` | `snowflake-connector-python` |
| `oracle` | `SCHEMA.TABLE` | `oracledb` (thin mode, no Oracle client needed) |

Every source is loaded as text so a bad value shows up as a DQ failure instead of a crash.

### Running against Snowflake / Oracle

Set `source_type` and `source_location` for a dataset in `dq_dataset_config`, then:

```bash
pip install snowflake-connector-python oracledb   # whichever you need
cp .env.example .env      # fill in the connection settings
set -a; source .env; set +a
python run_dq.py --db dq.db
```

Credentials are read from environment variables only - nothing is stored in the config tables.

## Report and alerts

```bash
python run_dq.py --db dq.db --report           # writes output/dq_report_<run_id>.html
python run_dq.py --db dq.db --report --alert   # also emails HIGH severity failures
```

The report shows summary cards (checks, passed, failed, high-severity failed) and a
table with failures listed first. `--alert` sends one email per run listing every failed
`HIGH` rule with the HTML report attached. SMTP settings come from `SMTP_HOST`,
`SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `ALERT_FROM` and `ALERT_TO`; if `SMTP_HOST`
is not set the alert is only logged, so local runs and CI don't need a mail server.

The process exits with code `1` when a HIGH rule fails, so a scheduler (Airflow, cron,
CI) can stop downstream jobs.

Sample output:

```
dataset    rule                      failed   pass%  status
------------------------------------------------------------
members    member_id_not_null             1    98.0  FAIL
members    member_id_unique               2    96.0  FAIL
members    zip_code_format                1    98.0  PASS
claims     paid_amount_range              1   99.17  PASS
claims     member_exists                  1   99.17  FAIL
...
```

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request:

1. **test** - `ruff` lint + full `pytest` suite on Python 3.10, 3.11 and 3.12
2. **dq-sample-run** - runs the framework end to end on the sample data and uploads the
   HTML report as a build artifact (open any run under the *Actions* tab to download it)

## Adding checks

See [docs/adding-a-rule.md](docs/adding-a-rule.md) - new checks are usually one `INSERT`,
new rule types are one function plus a registry entry.
